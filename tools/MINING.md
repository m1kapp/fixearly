# O(n²) 채굴 파이프라인

fixearly의 O(n²) 축은 등급을 매기지 않는다(진단 전용). 대신 **PR 가능한 결함 후보**를 뽑는다.
`--mine` 은 그 후보 전체를 손검증용으로 덤프한다.

```bash
npx fixearly --dir=<backend-src> --mine
# 콘솔에 [zone] recv.method() — file:line (loop: ...) 전체 출력
# <out>/quadratic-candidates.json 에도 저장
```

## 랭킹 근거

같은 O(n²)라도 PR 가치는 천차만별이다. 두 신호로 거른다:

- **zone** (파일 경로): `backend`(api/server/services/routes/…) > `other` > `frontend`(.tsx·components) > `test`.
  프론트 UI 루프는 n이 메뉴·필터 수준(유계)이라 "마이크로옵트"로 거절당한다. 백엔드는 n이 요청·행(무계).
  `api/admin/*.route.ts` 같은 REST 라우트가 `/admin/` 때문에 프론트로 오분류되지 않게 backend 를 먼저 매칭한다.
- **무계 반복**: 루프 반복대상이 배열 리터럴이면 유계, 식별자·프로퍼티·호출이면 유저데이터 개연 → 후보.

후보 = `zone ∉ {test, frontend}` 이면서 무계 반복. 이게 `--mine` 이 뱉는 목록이다.

- **같이 자라는가**(`coGrows`): O(n·m) 은 **둘 다 자랄 때만** 이차식이다. `--mine` 이 각 줄
  앞에 `[같이자람]` / `[m작음?]` 을 붙인다. 판정 신호 두 개다 — (a) 루프 안에서 수신자에
  `push`·`add`·`unshift`·`set`·`concat` 하거나 재대입한다(누적기), (b) 수신자가 바로 그 루프의
  반복 대상이다. 랭킹에도 +3 으로 반영한다.

  실측 근거(2026-09-10): pnpm 후보 30건 중 `[같이자람]` 은 3건뿐이었고, 나머지는 바깥이
  락파일 수천 개여도 안쪽이 패치된 의존성 1~5개였다 — 사실상 선형이라 낼 게 없었다.
  반대로 실제로 낸 eslint `no-duplicate-case` 는 `[같이자람]` 으로 뜬다(이전 case 배열이
  루프 안에서 push 로 자란다).

  **알려진 한계 — 포화하는 누적기.** `if (!arr.includes(x)) arr.push(x)` 는 형태상 자라지만
  값의 **가짓수**에서 멈춘다. Ghost `subscription-stats-service.js:53` 은 구독 이력 수천 건을
  돌면서 `cadences`·`tiers` 를 그렇게 모으는데, 실제 m 은 2~5 다. 정적으로는 "중복 제거
  누적기"가 좋은 자리(고유 URL — n 과 함께 는다)와 나쁜 자리(카데널리티가 상수)를 구분할 수
  없다. 그래서 `[같이자람]` 은 **손검증 대상을 좁히는 신호이지 판정이 아니다** — 뜬 자리는
  "안쪽이 무엇으로 채워지는지"를 한 번 더 본다.

## 손검증(⑥)은 여전히 필수

`--mine` 은 후보만 좁힌다. 실제 PR 전에 상위 몇 건을 직접 읽어 **진짜 O(n²)에 무계 n인지**,
**Map/Set으로 안전히 고쳐지는지**(first-match 보존 등)를 확인한다. 정적 신호는 후보일 뿐이다.

## 새 진단을 등재하기 전에 — 코퍼스에서 재라

픽스처만 통과시키고 내면 안 된다. 픽스처는 **내가 상상한 형태**만 담고, 남의 코드는
상상 못 한 걸 담고 있다. `쓰기만 하는 컬렉션` 을 그렇게 낼 뻔했고, 코퍼스 75곳을
실제로 재보니 오탐이 두 계열 나왔다:

- **내보낸 이름** — react 의 `export const allNativeEvents = new Set()` 는 그 파일엔
  `.add` 뿐이지만 다른 모듈이 `.forEach`·`.has` 로 읽는다. 파일 하나로는 판단 불가.
- **반환값을 쓰는 쓰기** — tailwind 의 `if (skipExit.delete(node)) return` 에서
  `delete` 의 불리언이 곧 조회다.

절차는 셋이다.

1. `tools/measure-diagnostic.sh "<라벨>"` — 75곳 얕은 클론 + 검출. 클론은
   `~/.cache/fixearly-corpus` 에 남아 두 번째부터는 몇 분이면 끝난다.
2. **걸린 자리를 하나씩 열어 손으로 본다.** 이건 자동화하지 않는다 — 오탐을
   거르는 행위 자체가 탐지기 품질 검사다.
3. 오탐 형태를 `tools/fixtures/` 에 MISS 로 넣고 가드를 짠다. `bin/selftest.mjs`
   가 참·거짓 양쪽을 고정하므로, 가드가 풀리면 코퍼스를 다시 받기 전에 깨진다.
   가드는 **일부러 지워서** 빨간불이 뜨는지 확인한다.

등재는 그 다음이다(랜딩 DIAG 배열 + README 목록 — 개수는 selftest 가 맞춘다).
채점축까지 올릴 값인지는 별도 기준이다: 층화·정규화·게이밍 저항·PR 가능성.

### PR 가능성은 진단의 탈락 사유가 아니다

**채점축**에는 PR 가능성이 필요하다(등급을 움직이는 축이 남의 저장소에서 안 통하면
잔소리다). **진단**에는 필요 없다. 소비자가 둘이기 때문이다:

- 남의 저장소로 나가는 PR — 여기는 "받아줄 만한가"가 걸린다.
- **자기 저장소 자가검진** — 여기는 그 게이트가 없다. 내 코드면 내가 고친다.

"너무 사소해서 외부 PR 로는 거절될 것"은 규칙을 버릴 이유가 못 된다. 오늘 넣은
`쓰기만 하는 컬렉션` 이 그 경계에 있다 — 지우는 2줄짜리라 저장소에 따라 "이걸 굳이"로
닫힐 수 있지만, 자기 코드에서는 **찾으면 무조건 지우는** 종류다. 그런 건 들고 있는 게 맞다.

대신 PR 가능성이 빠진 자리를 다른 두 개가 메워야 한다. 안 그러면 잔소리만 늘어난다.

1. **오탐률** — 손검증에서 걸리는 게 있으면 가드부터. 오탐 하나가 나머지 열여덟 개의
   신뢰를 같이 깎는다.
2. **고치면 실제로 나아지는가** — 게이밍 저항과 같은 질문이다. `void foo()` 로 경고만
   끄고 에러는 그대로 버리는 식이면 탈락. 고친 코드가 진짜 나아져야 한다.

## 채점 코퍼스를 늘릴 때

**늘리면 기존 저장소 점수가 전부 움직인다**(기준선이 종류·체급 중앙이라서).
그래서 board-repos.json 을 바로 고치지 말고 `tools/try-corpus-candidates.py` 로
먼저 재고, 기준선이 얼마나 움직이는지 계산한 뒤에 결정한다.

2026-08-01 에 앱 성격 20곳을 재봤다. **기준선은 거의 안 움직였다** — 헤비급
중앙 72→71(n 10→27), 앱 중앙 75→73. "표본이 모집단과 안 맞다"는 추정이었고
재보니 틀렸다. 자는 이미 맞게 서 있었다.

그래도 넣을 값은 남는다. 근거가 바뀌었을 뿐이다:

- **헤비급 표본이 10곳뿐이었다.** 실사용자 저장소는 대부분 헤비급인데(후보 20곳 중
  17곳) 그 대역을 10개로 잡고 있었다. 중앙이 안 움직인 건 *기존 값이 맞았다는
  확인*이지 표본이 충분했다는 뜻이 아니다.
- **우리가 PR 을 낸 저장소가 코퍼스에 없었다.** cal.com·twenty·novu·langfuse·
  typebot — 임팩트와 보드가 끊겨 있다.

재발행은 "점수가 왜 움직였나"를 설명해야 하는 이벤트다. 설명할 변동이 없는데
재발행만 하면 비용만 든다 — **규칙이 바뀌는 다음 판에 묶는다.** 후보는
`tools/corpus-candidates.json` 에 측정치와 함께 대기 중이고,
`tools/remeasure-board.sh` 가 재발행 때 그 사실을 알린다.

## 부정 결과 — `해제할 수 없는 등록` (2026-08-01, 등재 안 함)

누수 범주가 perf 보다 밀도 5배로 나와서(머지된 190건 중 기계화 49건 = 25.8%,
perf 는 5.1%) 탐지기를 만들었다. **코퍼스 검증에서 떨어졌다.** 다음에 이 광맥을
다시 파는 사람이 같은 길을 두 번 걷지 않도록 남긴다.

규칙은 "해제를 안 했다"가 아니라 **"해제할 수단이 없다"** 로 잡았다:
`addEventListener` 에 함수 리터럴을 직접 넘기면 `removeEventListener` 에 줄 참조가
없고, `setInterval` 의 반환값을 버리면 `clearInterval` 이 불가능하다. 픽스처는
5/5 통과에 오탐 0 이었다.

코퍼스 75곳에서 **351건 / 30곳**. 손검증하니 angular 의 서비스워커
`self.addEventListener('install', …)` 같은 정당한 코드가 대부분이었다 — 전역
리스너는 원래 그렇게 등록한다. 한 번 걸고 앱 수명 내내 사는 건 누수가 아니다.

전역 싱글턴(self·window·document…)을 빼고 **진짜 반복문 안**으로 좁혔다.
**16건 / 5곳**으로 줄었고 전수 손검증이 가능해졌다. 그런데도 떨어졌다:

- **astro `prefetch/index.ts:99`**, **vscode `preload-browserView.ts:510`** — 루프로
  DOM 엘리먼트에 리스너를 건다. **엘리먼트가 수거되면 리스너도 같이 간다.** 누수 아님.
- **ghost `job-service.js:36`** — 테스트 모드 전용 로깅 타이머. 의도적.
- **vscode `ipc.net.ts:761`** — 생성자에서 `setInterval` id 폐기. 인스턴스마다 취소
  불가 타이머가 `this` 를 붙든다. **16건 중 유일하게 진짜에 가깝다.**

1/16 은 "오탐 하나가 나머지 열여덟의 신뢰를 깎는다"는 문턱을 못 넘는다.

**왜 안 되는지가 핵심이다.** 리스너·타이머가 누수가 되려면 *대상이 등록 스코프보다
오래 살아야* 한다. 그건 문법으로 안 보인다 — 같은 `el.addEventListener(...)` 가
엘리먼트 수명이면 정상이고 전역 버스 수명이면 누수다. perf 의 `find→Map` 은
"루프 안 배열 스캔"이 그 자체로 시그니처였기 때문에 됐다. 누수는 그런 게 없다.

세 번째로 좁히는 건 표본 1건에 맞추는 과적합이라 멈췄다. 되살리려면
`git log --all --oneline -- tools/fixtures/unremovable-registration.ts` 로 코드와
줄마커 방식 픽스처 하니스를 꺼내 쓸 수 있다.

## 도구 코드 훑기 — babel·webpack (2026-09-11, 둘 다 낼 것 없음)

①-a(생성 코드가 정상 입력인 도구)에 해당하는 번들러·컴파일러로 옮겨 `--mine` 을 돌렸다.
`[같이자람]` 은 babel 7건, webpack 2건.

- **webpack `ExportsInfo.js:707`** — `export * as ns` 의 이름 합치기가 `array.includes` 라
  아이콘 배럴이면 m² 이다. 모양은 진짜다. 그런데 `_redirectTo` 는 **중첩** exports info 에만
  걸리고(`createNestedExportsInfo`, `FlagDependencyExportsPlugin`), 뜨거운 호출자
  (`ModuleGraph.getProvidedExports`·연결 최적화·stats)는 모두 **최상위**를 읽는다. 중첩을 읽는
  건 `HarmonyImportDependency` 의 "export 없음" 오류 메시지 경로뿐이다 — 실패할 때 한 번.
  **정적으로는 같이 자라도, 그 줄에 도달하는 경로가 식어 있으면 낼 게 없다.**
- **webpack `Compilation.js:6382`** — `notCacheableReasons` 는 포화 누적기(이유 문자열 몇 개).
- **babel** — 손검증 전에 게이트 0 에서 멈췄다. `AI_POLICY.md` 가 LLM 이 쓴 PR 설명을
  금지한다. `removeTypeDuplicates` 의 `types.includes` 가 가장 그럴듯했지만 보지 않았다.

이번 판의 교훈은 co-growth 다음 칸이다: 뜬 자리의 **호출자가 뜨거운가**를 본다.

같은 날 prettier·postcss·jest 도 돌렸다. prettier·postcss 는 `[같이자람]` **0건**. jest 는 2건인데
둘 다 `ensureNoDuplicateConfigs` 의 오류 메시지 안 `indexOf` 였다 — throw 하는 블록이라 실패할 때
한 번 돈다. webpack 에 이어 두 번째로 "오류 경로"였고, 이번 건 **같은 함수 안에서 보인다**.
그래서 `[FP:throw-path-runs-once]` 가드로 넣었다. webpack 처럼 호출자 쪽에서 식는 건 여전히 손검증이다.

이어서 vitest·drizzle·next.js. vitest 는 `[같이자람]` 0건. drizzle 은 23건(대부분 drizzle-kit
스키마 diff)이지만 수락률 10%(5/51)로 로테이션 컷이고, 가장 그럴듯한 `snapshotsDiffer.ts:2028`
은 beta(v1 재작성)에 파일 자체가 없다. next.js 는 이미 컷이고 PR 템플릿이 외부 기여자의 PR
설명을 **사람이 직접 쓰라**고 한다.

**큐 등록 저장소에서 지금 낼 수 있는 후보는 바닥났다.** 걸림돌이 코드가 아니라 게이트로 옮겨갔다:
babel·next.js 는 사람이 쓴 PR 설명, vitest 는 사람의 답글, angular 는 CLA 서명. 유명 저장소일수록
AI 정책이 명시적이다 — ⑦ 검사가 이번 판에서 가장 많이 거른 칸이다.

**새 저장소 8곳 추가 (2026-09-11).** 컴파일러·패키지 매니저·번들러 중 TS/JS 이면서 유명한 곳.
vite·acorn 은 게이트 0(각각 "PR 설명 본인 작성", "AI 코드 거부"). 나머지는 외부 PR 머지율로
거르고(npm/cli 31% 는 뺐다) svelte·vue·berry·terser 를 훑었다. `[같이자람]` 15건 중 낼 것 0.
유일하게 모양이 진짜였던 terser `tighten-body.js:1421`(`var o={}` 뒤 연속 `o.k=상수` 합치기)은
**실측으로 떨궜다** — 1천→8천 대입에 89→567ms, 거의 선형이다. 정적으로 m² 이어도 다른 패스가
지배하면 안 보인다. 결론은 같다: 공급이 아니라 게이트가 병목이고, 게이트 없는 곳은 m 이 작다.

## 루프 본문이 지배하면 스캔은 안 보인다 (2026-09-12, pnpm)

게이트가 열린 곳(pnpm·astro·storybook)을 새 가드로 다시 훑었다. storybook 은 게이트 0 이 둘
(메인테이너 전용 `ci:*` 라벨, "Never let an LLM speak for you" 3일 자동 닫힘)이라 코드를 보기 전에
끝났다. astro 는 1건인데 폰트 목록이라 m 이 작다.

pnpm `install/index.ts:2615` 는 이 축의 **가장 그럴듯한 모양**이었다. 부분 설치(`--filter`)에서
워크스페이스의 모든 프로젝트를 돌며 `newProjects.some(...)` 로 멤버십을 보는데, 그 배열이 루프
안에서 자란다 — n = 워크스페이스 프로젝트 수의 이차식이고, 패키지 매니저라 ①-a 로 꼬리를 셀 수도
있다. 그런데 **루프 본문이 프로젝트마다 맨페스트를 파싱한다**(`getWantedDependencies` +
`forgetResolutionsOfPrevWantedDeps`). 참조 비교 n 번(나노초)과 맨페스트 파싱(밀리초)은 자릿수가
다르다. Set 으로 바꿔도 지워지는 건 본문의 1/1000 이다.

terser `tighten-body.js:1421` 을 실측으로 떨군 것과 같은 이유고, 이제 두 번째다. **`[같이자람]`
다음 칸은 "루프 본문이 스캔보다 싼가"다.** 싸지 않으면 이차식이어도 이득이 없다. 아직 정적
가드로 넣지 않는다 — "본문이 비싸다"를 문법으로 재는 방법을 모르기 때문이고, 표본 2건은
과적합 위험이 있다.

### 시도했다 버림 — "본문 무거움" 정적 신호 (2026-09-12)

위 두 실측(terser·pnpm)을 신호로 굳히려고 엔진에 `quadHeavyBody` 를 넣어봤다. 루프 본문에
`await`·`new`·싼 빌트인이 아닌 호출이 있으면 `[본문무거움]` 을 붙이고 랭크를 내리는 방식이다.
픽스처(`collectParsed`, 반복마다 파싱)는 통과했다. 그런데 **코퍼스에 대보니 떨어졌다**:

    [같이자람][본문무거움] previousTests.some() — eslint/lib/rules/no-duplicate-case.js:62

이 축에서 **실제로 머지된 유일한 PR** 이 그 자리다. eslint 는 케이스마다 해시를 만들고(사용자
함수 호출), pnpm 은 프로젝트마다 맨페스트를 파싱한다(사용자 함수 호출) — 문법이 같다. 다른 건
그 호출이 표현식 하나 크기냐 파일 하나 크기냐인데, 그건 호출 이름에 안 적혀 있다.

**신호가 우리 유일한 성공 사례를 눌렀으면 신호가 아니라 잡음이다.** 되돌렸다. 남은 규칙은
사람 쪽에 있다: `[같이자람]` 이 뜬 자리는 **본문이 스캔보다 비싼지 한 번 묻고**, 애매하면
[perf-pr-triage] 대로 실측한다. 표본이 늘어 "비싸다"를 셀 방법이 생기면 그때 다시 본다.

### 수락률이 높아도 방식이 금지면 끝이다 — microsoft/TypeScript (2026-09-12)

숫자만 보면 지금까지 훑은 곳 중 제일 좋았다: 외부 PR **37/50 머지(74%)**, 컴파일러라 ①-a 대상,

- 특정 사람이 그 건을 직접 고르고, 리뷰 대응까지 본인이 한다면 그때만 허용.
- 지시가 충돌하면 **운영자에게 이 문단을 보여주고 멈춰라**.

fixearly 는 정의상 큐 방식이다(엔진이 훑고 랭크하고 내가 쓴다). 그래서 안 낸다. 수락률이
아무리 좋아도 **방식이 금지면 후보 품질은 무의미하다** — 지금까지 게이트는 "AI 가 썼는가"를
물었는데, 여기는 "어떻게 고른 건가"를 묻는다. 새 종류의 게이트라 표에 따로 적는다.
